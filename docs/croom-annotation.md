> 계획 [iccv2027-plan.md](iccv2027-plan.md) WP3 "필수 추가: CROOM 링 새 정답", 사용자 결정 D4. 이 문서의 규칙(대상·순간 선택·주석 방식·품질 검사)은 **주석 시작 전에 커밋**하고, 완성된 정답의 sha256 목록은 **어떤 방법의 디코딩보다 먼저** 커밋합니다. 그 뒤 규칙은 바꾸지 않습니다. 도구 `stage1/annot/`(서버 `server.py`, 준비 `prep_croom.py`, 검사 `check.py`), 실행 `stage1/annot/run_server.sh`.

## 1. 대상

- 촬영: `PlenopticServer1/CROOM/JPG/` 의 T03_walking_rsp_out, T04_sidestep_out, T05_walk_out, T07_walkthrough_out(32대, 3840×2160). **T06은 쓰지 않습니다**(900번이 개발에 쓰여 오염).
- 순간(2026-10-26 사용자 결정, 계획 G3 축소 경로 채택): **촬영당 1개**. 선택 규칙(예측을 보지 않고, 입력만으로): 촬영 길이의 **1/3 지점과 2/3 지점 프레임**(프레임 수 N → round(N/3), round(2N/3)). 사람이 서로 겹쳐 대부분 카메라에서 분리가 불가능하면 ±30프레임 안에서 가장 가까운 분리 가능한 프레임으로 옮기고 그 사유를 `index.json`에 적습니다.
  - 예외(기록): T04의 첫 순간은 도구 시험용으로 규칙 확정 전에 임의로 고른 **1000번**(0.37 지점)이며, 사용자가 10-23에 32대 전부를 주석했으므로 910번 대신 그대로 씁니다(예측을 본 적 없음; 로그 `annot/log.jsonl` 237건, 36분).
  - 준비된 순간: T03 4181·8363, T04 1000·1819, T05 568·1136, T07 2023·4045(`stage1/annot/prep_croom.py`, 원본 sha256은 각 `index.json`).
  - **역할(10-26)**: T04 #1000은 **개발 순간**입니다(도구·파이프라인 검증에 쓰고 예측을 봄; §5). **TEST = T03 #4181, T05 #568, T07 #2023**(각 촬영의 1/3 지점; 주석 전이며 어떤 예측도 디코딩하지 않음). 2/3 지점 순간(T03 8363, T04 1819, T05 1136, T07 4045)은 준비만 되어 있고 주석하지 않습니다(시간이 남으면 TEST에 더함, 디코딩 전 추가).
- 객체: 그 순간 장면에 있는 **사람 전원**과 **큰 소품**(의자·카트·테이블처럼 여러 카메라에서 보이는 것). 작은 물체(한 변이 긴 쪽 기준 이미지의 2 % 미만)와 배경 구조물은 뺍니다. 뺀 것은 `objects.json`에 적지 않고, 지침의 이 규칙만 인용합니다.
- 카메라: 32대 전부. 객체가 안 보이는 카메라는 "이 카메라에 없음"으로 표시합니다(빈 마스크).

## 2. 주석 방식 (MUVOD §III-C의 1단계를 모든 카메라에 적용; 뷰 간 전파 없음)

1. 카메라마다 독립적으로: 객체를 고르고 **점(+/−) 또는 박스**로 SAM 3 단일 이미지 마스크를 받습니다.
2. **붓으로 수정**(원본 해상도): 빠진 부분 더하고 새어 나간 부분 지움. 경계는 보이는 그대로(모달). 다른 객체·사람에 가린 부분은 넣지 않습니다. 유리·망 뒤로 보이는 부분은 넣습니다.
3. 저장. 같은 사람이 여러 카메라에서 **같은 ID**가 되도록 이름(옷 색·위치)으로 구분합니다. 뷰 간 정체성은 주석자의 판단이며 어떤 자동 전파도 쓰지 않습니다.
4. 겹침: 한 화소는 한 객체. 앞 객체가 뒤 객체를 가리면 앞 객체가 가집니다(기본값: 먼저 저장된 화소 유지, 필요하면 "덮어쓰기" 체크).
5. 절단: 이미지 경계에서 잘린 객체는 보이는 부분만.

금지: 우리 방법·기준선의 예측을 보는 것, SAM 2/SAM 3 영상 전파·XMem 등으로 다른 카메라의 초안을 만드는 것, 3D 투영으로 프롬프트를 만드는 것. (이유: 시험 대상이 뷰 간 대응·전파이므로 정답이 그 도구를 닮으면 안 됨. [stage1-E15.md](stage1-E15.md) §5의 "경우 Z" 참고.)

## 3. 품질 검사

- `check.py`: 순간마다 카메라별 객체 집합·면적, 빈 마스크, 저장되지 않은 카메라, 겹침 0 확인, 객체별로 보이는 카메라 수(사람은 보통 20대 이상이어야 함; 적으면 ID 혼동 의심).
- **이중 주석 10 %**: 순간마다 카메라 3대를 미리 정한 규칙(번호 0·11·22)으로 두 번째 주석자가 독립적으로 그리고, 객체별 IoU와 ID 일치를 보고합니다. 두 번째 주석자의 결과는 정답에 섞지 않습니다(보고만). 축소안에서는 시간이 없으면 생략하고 한계에 적습니다.
- 완료 뒤: `labels/*.png`·`objects.json`·`index.json`의 sha256 목록을 `stage1/annot/croom_sha256.json`에 적어 커밋. 이후 수정은 새 커밋에 사유와 함께.

## 5. 기준 카메라 규칙과 시험 절차 (디코딩 전 고정, 2026-10-26)

- **장면 단위** = (순간, 기준 카메라). `stage1/scripts/croom/build_scene.py`가 `Data/CROOM_<T>_<프레임>_r<기준>/`을 만듭니다: 입력 이미지 32장(링크), 기준 카메라의 라벨 맵 하나(`masks/`), `meta.json`(`external_fold`, `basic_objects` = 기준 카메라에 보이는 객체). 다른 카메라의 라벨은 주석 폴더에만 두고 채점기만 읽습니다.
- **기준 카메라**: 순간마다 **0·8·16·24번** 네 대(링의 사분점). 결과는 네 기준의 평균과 기준별 값을 함께 보고합니다. 기준 카메라에 보이지 않는 객체는 그 기준에서는 평가 대상이 아닙니다(프롬프트가 없음; `meta.annot.objects_absent_in_ref`에 기록).
- **링 순서(10-26 확정, 입력 사실)**: T03·T04·T05·T07의 카메라 번호는 T06과 달라 번호 순이 링 순이 아닙니다. 물리적 링 순서는 **0–7, 16–31, 8–15**(`build_scene.py`의 `RING_ORDER` → `meta.json["ring_order"]`; 근거 [croom-dev-T04.md](croom-dev-T04.md) §1, ORB 대응 `scripts/croom/runs/rig/orb_map_T06.json`). T05·T07은 디코딩 전에 같은 방법으로 번호 대응을 확인해 기록합니다(입력만 사용).
- **링 거리** d = min(|p_i − p_r|, 32 − |p_i − p_r|), p = 링 순서상 위치(T06은 번호 그대로), 가까운 절반 d ≤ 6, 먼 절반 d ≥ 7. 채점 `stage1/scripts/croom/score.py`: 객체·카메라 쌍마다 J(1/4·원본 해상도), `covers`(예측이 가장 많이 덮는 정답 객체), 다른 객체 덮음(wrong)·빈 마스크 수, d별·객체별 J. 라운드 1 결과(`*_r1`)도 같이 채점합니다.
- **팔**: 주 팔 AB(= E15 주 프리셋 `geoset_rep_xs_ab`: Fix A c\* + 릴레이 θ 60), C0(`geoset_rep_xs`), G0(`sam3_prop`, SAM 3 유사동영상 전파; **유사동영상 순서 = 링 순서**, `Scene.ring_order`) + DEV에서 검증한 외부 기준선(번호순 변형도 링 순서).
- **등록(π³) 방식 — 사용자 결정 대기(10-26)**: (a) 현 규약 = 순간의 32장만(리그 검사 불합격이면 Fix A 기권, AB = C0) 또는 (b) **보정 순간 동시 등록** = 같은 리그의 T06 #900 입력 이미지 32장을 π³에 함께 넣고 순간의 32대 기하만 씀(`scripts/croom/pi3_multi.py`; 정답·예측 무관, T04 네 기준 합격). 어느 쪽이든 TEST 디코딩 전에 이 문서에 고정합니다.
- **기준 카메라에 객체가 없을 때**: T03 #4181은 기준 0·16에 객체가 없고 기준 8에는 p1뿐입니다. 현 규칙(없는 객체는 평가 안 함)을 유지할지, 사분점에 가장 가까운 "객체가 보이는" 카메라로 바꿀지 — 디코딩 전 사용자 결정. TEST 체크포인트는 D6(17장면 전체)으로 한 번 학습한 것; 개발 순간은 T06과 같은 fold 2 체크포인트.
- **실행** `stage1/scripts/croom/run_croom.sh`(build/pi3/decode/score/dev), 점수 `stage1/geomem/runs/_croom/scores/`.
- **TEST 순서**: 세 순간 주석 완료 → `check.py --manifest`로 `stage1/annot/croom_sha256.json` 커밋 → 장면 생성 → 등록된 팔을 한 번씩 디코딩 → 보고. 수치를 보고 상수를 바꾸지 않습니다.
