# MVOpt ↔ OneStageNew 변경 감사

**질문.** MVOpt는 OneStageNew에 메모리 수정만 넣은 것인가? 그대로 되돌려 넣어도 되는가?

> **결론과 후속.** 답은 "그렇다"였고, **2026-09-04에 실제로 반영했습니다.**
> 두 폴더는 이제 바이트 동일하며 OneStageNew는 동결 스냅샷입니다.
> 아래 "되돌려 넣을 때 알아야 할 것"은 이미 수행된 판단의 근거로 읽으십시오.

**방법.** 변경 7종 각각에 분석자 1명 + 서로 다른 관점의 반증자 3명(도달가능성 / dtype·수치 / 객체수명·공유상태).
반증자는 "반증하라"는 지시를 받았고, 구체적이고 **도달 가능한** 경로를 제시할 때만 반박으로 인정했습니다.
에이전트 32개, 도구 호출 1,015회.

## 판정

| 변경 | 분류 | 출력 보존 | 반박 |
|---|---|---|---|
| S1 sentinel | 순수 메모리 수정 | ✓ | 0/3 |
| S2 mask_inputs 제거 | 순수 메모리 수정 | ✓ | 0/3 |
| S3 meta 자리표시자 | 순수 메모리 수정 | ✓ | 0/3 |
| S4 bool 빠른 경로 | 순수 메모리 수정 | ✓ | 0/3 |
| S5 fp32 캐스트 | 순수 메모리 수정 | ✓ | 0/3 |
| S6 RetireSpatialPredictor | 메모리 수정 **+ 새 공개 API** | ✓ | 0/3 |
| S7 TRIM_CACHED_OUTPUTS | **새 기능** | 조건부 | 1/3 |

**결론: 사용자의 전제는 맞습니다.** S1~S5는 알고리즘 변화가 없습니다.
S6·S7은 순수 수정이 아니므로 별도 판단이 필요합니다.

S1은 특히 안전합니다 — upstream SAM 3가 `sam3_video_inference.py:400`에서 하는 것과 같고,
같은 저장소의 형제 패키지 3개(OneStage, TwoStage, TwoStageNew)가 이미 동일 형태를 쓰고 있습니다.

## 되돌려 넣을 때 반드시 알아야 할 것

### S6은 짝으로 움직입니다

`RetireSpatialPredictor`와 `uses_spatial_predictor`는 한 쌍입니다.
메서드만 복사하고 플래그를 빠뜨리면, 폐기 후 속성 검사가 틀린 분기를 골라
`SCSam3VideoPredictorNewMem.py:100`에서 `KeyError: 'session_ids'`로 죽습니다.

**새로 생기는 실패 양상** (원본 OneStageNew에는 없던 것 — 반영 후에는 그 폴더에도 존재):

- 폐기 후 `predictor_spatial`이 `None`이라, `runMVSeg.py:144`의
  `getattr(self, "predictor_spatial", self.predictor)` 대체 경로가 **작동하지 않습니다**
  (속성이 존재하되 `None`이므로). `del`이었다면 문서대로 동작했을 것입니다.
- 폐기 후 `AddPoint`·`AddText`·`InitializeSegmentation`·`LoadVideo_*`가 전부 `None`에서 죽습니다.
- 한 인스턴스로 시점 전파를 **두 번 돌릴 수 없습니다.** 데이터셋마다 인스턴스를 재사용하는 배치 루프는 깨집니다.

현재 러너는 폐기 이후 이것들을 호출하지 않으므로 안전합니다. 순서를 바꾸면 깨집니다.

### S7은 실제로는 켜진 채로 돌았습니다 ★

`runMVOptThree.sh:14`에 `-e SCSAM3_TRIM_CACHED_OUTPUTS=1`이 있습니다.
**MVOpt 결과 전부가 이 스크립트로 만들어졌으므로, "기본 꺼짐"은 실제 실행 조건을 설명하지 못합니다.**

직접 확인했습니다 (2026-09-04):

```
Blocks, 트림 명시적 OFF vs 저장된 MVOpt 출력
→ 882 PNG 대 882 PNG, 완전 일치
```

즉 이 배치 경로에서는 ON/OFF가 같은 출력을 냅니다. 발표 수치에 영향 없습니다.

**그러나 docstring의 안전장치 주장 하나는 거짓입니다.**
`propagation_full` 가드는 **이 패키지에서 절대 발동하지 않습니다** —
`add_prompt`가 항상 첫 전파보다 먼저 실행되어 `action_history`가 비어 있지 않으므로
`parse_action_history_for_propagation`이 `propagation_full`을 반환할 일이 없습니다.

**대화형 경로의 잠재 위험** (배치 러너에서는 도달 불가):

- 같은 프레임에 두 번째 객체를 프롬프트한 뒤 다시 전파하면, 첫 객체가 사라질 수 있습니다.
- 손상이 **조용합니다** — `.get(frame_idx, {})`로 읽고 빈 항목을 다시 만들기 때문에
  예외가 아니라 빈 마스크로 나타납니다.
- 손상이 **영구적입니다** — 이후 `_cache_frame_outputs`가 잘린 상태를 되씁니다.
- 값 파싱이 함정입니다: 거짓으로 취급되는 것은 `""`·공백·`"0"`뿐입니다.
  **`"false"`, `"off"`, `"no"`, `"00"`은 전부 켜집니다.**
- 플래그는 import 시점에 한 번 읽습니다. 프로세스 안에서 `os.environ`을 바꿔도 효과가 없습니다.

**권장.** 대화형 데모에서는 켜지 마십시오. 배치 실행에서만 쓰십시오.

#### 완전성 비평의 오판 — 그리고 실제 증거

감사의 완전성 비평자는 "S7은 어느 방향으로도 출력 동등성 증거가 전혀 없다"를 **최대 공백**으로 지목했습니다.
근거는 "12개 바이트 동일 실행은 `runMVSegAll.sh`가 했고 그 스크립트는 `-e`를 넘기지 않으므로 트림 OFF였다"는 것이었습니다.

**틀렸습니다.** 로그 디렉토리 명명이 스크립트를 특정합니다:

| 스크립트 | 로그 디렉토리 | 트림 |
|---|---|---|
| `runMVSegAll.sh:46` | `logs/mvseg-*` | 설정 안 함 |
| `runMVOptThree.sh:7` | `logs/mvopt-*` | **ON** |
| `runForSam2Three.sh:7` | `logs/forsam2-*` | 설정 안 함 |

12개 데이터셋 MVOpt 실행은 `logs/mvopt-20260904-060418`, 무거운 3개는 `logs/mvopt-20260904-010657` —
**둘 다 `runMVOptThree.sh`이므로 트림 ON입니다.**

따라서 실제 증거 상황은 이렇습니다:

| 대조 | 규모 | 결과 |
|---|---|---|
| MVOpt(**트림 ON**) vs OneStageNew(당시 트림 기능 없음) | 12개 데이터셋 · PNG 12,692장 | **차이 0** |
| MVOpt(트림 ON, 저장본) vs MVOpt(**트림 명시적 OFF**), Blocks | PNG 882장 | **차이 0** |

비평자가 비어 있다고 본 칸은 이미 채워져 있었고, 12개 데이터셋 규모입니다.
비평자의 정적 분석(가드가 죽어 있다, 대화형 경로에 조용한 손상 가능성)은 여전히 유효하며 위에 반영했습니다.

## 남은 잠재 위험 (오늘은 도달 불가)

각 변경은 "아무도 이 값을 읽지 않는다"는 불변식에 의존합니다. 그 불변식을 지키는 **단언문이나 테스트가 없습니다.**

| 변경 | 무엇이 깨뜨리는가 |
|---|---|
| S1 | 저장된 값을 소비하는 독자 추가 (문자열에 `TypeError`) |
| S2 | "이 객체가 마스크로 프롬프트됐나"를 이 딕셔너리 크기로 판정하는 코드 |
| S3 | 트래커 상태 전체를 CPU로 오프로드하는 최적화 → `Cannot copy out of meta tensor` |
| S3 | `torch.where`·`torch.stack`은 meta 텐서를 **조용히 통과시킵니다** — 오류가 먼 곳에서 납니다 |
| S4 | 반환값을 int64 버퍼에 넣거나 `.dtype`을 검사하는 호출자 |
| S5 | 백본 입구에 in-place 정규화 추가 → NEW는 저장된 프레임을 덮어씁니다 (별칭이 생기므로) |
| S6 | 폐기 이후 교차시점 API 호출 |

S3은 특히 주의가 필요합니다. 이 패키지들은 upstream 파일을 **상속이 아니라 복사**했으므로,
upstream을 올릴 때 충돌로 드러나지 않습니다.
