# 사전 등록 — 중앙 기준 카메라에서 이웃 방향 재절제 (P4 재개, E4)

> **이 문서는 GPU 실행 전에 커밋됩니다.** 판정·감시값·기대값을 여기 적힌 대로 읽고 실행 뒤 바꾸지
> 않습니다. P4(2847fd2)·P12(011fa86)·P5(1a4bba8)와 같은 규율입니다.

## 0. 왜 다시 하는가 — P4의 결론이 조건부였기 때문

[phase3-neighbourhood.md](phase3-neighbourhood.md)의 P4 절제는 모드 A~E를 전부 돌렸고 결론은
**"규칙상 A 유지"**였습니다. 그 결론이 낸 관찰이 이번 실험의 근거입니다.

> 방향은 효과가 있고, 그 효과는 **"이웃이 없던 카메라"에서만** 납니다. 인덱스 0 카메라(대개 기준
> 카메라)는 A에서 이웃 0개였습니다. 위쪽 이웃 하나를 주면(B·C·E) Fencing v0의 J가 0.79 → 0.89~0.90으로
> 회복됩니다. (P4 §5)

**그때 그 카메라는 장면당 하나였습니다.** P4는 예전 기준 카메라(max-id 규칙)에서 돌렸고, 그 규칙은
동점이면 `cam_list`의 첫 항목을 골라 사실상 리그 **끝**을 기준으로 삼는 일이 많았습니다(Fencing v0,
Blocks cam9, Painter v15). 기준이 끝에 있으면 모드 A(뷰 v가 v−1을 읽음)에서 거의 모든 카메라가
**기준 쪽**을 읽고, 이웃이 없는 카메라는 하나뿐입니다.

**c_ini는 리그 중앙입니다.** 그래서 기준보다 번호가 낮은 카메라는 A에서 **기준의 반대편, 즉 시드가
더 나쁜 쪽**을 읽습니다. 오늘 세어 보니 채점 카메라 51대 중:

| | 대수 |
|---|---|
| A에서 이웃이 아예 없음 (뷰 인덱스 0) | **9** |
| 기준보다 낮아 "먼 쪽"을 읽음 (인덱스 0 포함) | **15** |
| 기준 쪽을 읽음 | 36 |

P4에서 효과가 났던 부류가 9대이고, 방향이 불리한 부류까지 넓히면 15대입니다. **P4의 결론은 그 기준
카메라 집합에 대해서만 유효했고, 지금 조건에서는 다시 물어야 합니다.**

## 1. 무엇을 돌리나

- **처치**: `SegMaskSam3XW1CGPS4M` — 채택 구성에 **모드 C**를 더한 것.
  모드 C = 아래 이웃은 프레임 t, 위 이웃은 프레임 t−1 (`--xview-mode C`).
- **대조**: `SegMaskSam3XW1GPS4M` (채택 구성, 모드 A). 이미 있습니다.
- 나머지는 전부 동일: W=1, 게이트·이웃 포인터·꼬리표 이동 4, `--track-cams closure`,
  `--ref-cam muvod`, MUVOD basic 프로토콜, 17장면.

**왜 C 하나인가.** P4에서 B·C·E가 모두 S1(Fencing v0 ≥ 0.85)을 통과했고 헤드라인은 C와 E가 같았으며
(0.8468) E는 C 대비 이득이 없으면서 두 배 비쌌습니다. B는 아래 이웃까지 t−1로 미뤄 현재 프레임 정보를
버립니다. **C가 P4의 승자 후보였고 비용이 A와 같습니다.** 모드를 여럿 돌리면 다중비교가 되고, 이번
질문은 "방향을 양쪽으로 열면 c_ini에서 달라지는가" 하나입니다.

## 2. 엔드포인트와 판정 — 실행 전에 고정

| 이름 | 읽기 | 대조 |
|---|---|---|
| **E4-0 (1차)** | MUVOD basic J&F³ 17장면, `C − A`, 장면 짝지음, 클러스터 CI | 모드 A |
| **E4-1 (메커니즘)** | **A에서 이웃이 없던 9대**의 카메라 J&F 평균, `C − A` | 〃 |
| 보조 | 기준보다 낮은 15대 / 기준 쪽 36대로 나눈 Δ, complete 표, 유실 회복 사건(E3 스크립트) | |

**채택**(헤드라인을 C로 바꿈)은 **둘 다** 참일 때:

- **(a) E4-1**: 이웃 없던 9대의 Δ가 **양수이고 클러스터 95% CI가 0을 제외**. 이것이 메커니즘 조건입니다.
  이 9대는 A에서 이웃 입력이 0개였으므로 C에서 달라지지 않으면 실험이 무의미합니다.
- **(b) E4-0**: 17장면 평균 Δ **≥ 0**이고 어느 장면도 Δ **< −0.005**가 아님. P5와 같은 방어선입니다.

(a) 통과·(b) 실패 → "방향은 그 카메라들을 고치지만 다른 곳을 망가뜨린다"로 보고하고 채택하지 않습니다.
(a) 실패 → **P4의 결론(A 유지)이 c_ini에서도 유효**하다고 확정하고 이 줄기를 닫습니다.

## 3. 감시값

| | 기대 | 어긋나면 |
|---|---|---|
| S1 | **기준 쪽을 읽는 36대 중 뷰 인덱스가 c_ini보다 큰 카메라**는 A와 C에서 아래 이웃이 같고 위 이웃만 더해짐 — Δ가 0일 필요는 없으나 부호가 한쪽으로 쏠리면 기록 | — (기록만) |
| S2 | closure 세션 수가 A보다 큼 (C의 의존 원뿔은 `max(scored)+W·(num_frame−1)`) — 실행 로그로 확인 | 배관 오류 |
| S3 | 모드 C 폴더 이름에 `C`가 들어감(`SegMaskSam3XW1CGPS4M`), A 폴더를 덮어쓰지 않음 | 즉시 중단 |
| S4 | 기준 카메라(c_ini)의 J&F 변화가 **−0.005 이내** | 방향 변경이 기준을 망가뜨림 |

## 4. 기대값 (P4에서 옮겨온 것, 주장 아님)

P4에서 C는 예전 기준 카메라 15장면에서 헤드라인 0.8468(A 0.8450 대비 +0.0018)이었고 Fencing v0가
0.79 → 0.89였습니다. c_ini에서는 그 부류가 1대에서 9대로 늘었으므로 **E4-1이 더 크게, E4-0도 더 크게**
나오는 것이 가설입니다. 반대로 기준 쪽 36대에서 손해가 나면 상쇄될 수 있습니다.

## 5. 실행

```bash
cd SCSam3
XVIEW=1 XMODE=C XGATE=1 XPTR=1 XSHIFT=4 TRACK=closure XREF=muvod LOGTAG=e4-modeC \
  ./runMVOptThree.sh <17개 장면>
```

채점·판정:

```bash
docker run --rm --user $(id -u):$(id -g) -v /:/host -w /host$PWD scsam3 \
  python eval/eval_jf.py --methods SegMaskSam3XW1GPS4M SegMaskSam3XW1CGPS4M \
    --out /host$PWD/Data/MVSeg/jf_e4.json
python3 eval/e4_judge.py --raw Data/MVSeg/jf_e4.json
```

GPU 한 스윕. 모드 C는 closure 세션이 A보다 많아 A(약 45분)보다 오래 걸립니다.

## 6. 이 실험이 답하지 않는 것

- 모드 B·D·E는 돌리지 않습니다. 질문은 "양방향이 c_ini에서 달라지는가" 하나입니다.
- W>1은 돌리지 않습니다(Phase 2에서 W=1 포화 확인).
- 손잡이 없는 순수 C(`XW1C`)는 돌리지 않습니다. 채택 구성 위에서의 증분만 봅니다.
