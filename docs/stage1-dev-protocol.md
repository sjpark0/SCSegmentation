## 1. 집합

| 이름 | 프레임 | 용도 |
|---|---|---|
| **TEST** | 각 장면의 기준 프레임(meta `ref_frame`) — 키프레임 664쌍(`MVSeed/runs/seedfail.json`) | 사전 등록한 관문(G1/G2 …)만. 무엇도 여기서 고르거나 조정하지 않음 |
| **DEV-A** (탐색) | 기준 프레임이 아닌 학습 프레임의 [3::4] = ref+4, +8, +12, +16, +20 (장면당 5) | 후보 측정, 상수 고정, 상한 추정. 반복 사용 가능 |
| **DEV-B** (확인) | 나머지 비기준 학습 프레임 15개(ref+1, 2, 3, 5, 6, 7, 9, …, 19) | 등록 하나당 한 번, DEV-A에서 고른 규칙을 확인. 확인 결과를 보고 규칙을 바꾸면 DEV-B는 소진된 것으로 봄 |

- 뷰 = (프레임 t, 카메라) — 주석된 비기준 카메라 2대. 입력 = 기준 카메라 c_ini의 t 시점 정답(장면의 basic 객체 집합으로 제한). 쌍 = (장면, t, 카메라, 객체), c_ini에 객체가 있고 그 카메라 정답이 비어 있지 않은 것(키프레임의 gt_px > 0 규칙과 같음).
- 장면마다 **자기 폴드를 보류한 체크포인트**로 디코딩하므로 DEV 프레임은 그것을 디코딩하는 모델의 학습 데이터에 들어 있지 않습니다(다른 폴드 모델의 학습에는 들어 있음 — 키프레임과 같은 조건).
- DEV-A 3 300쌍(채택 `geoset_rep_x` J&F 0.908), DEV-B 약 3 배.

## 2. 도구 (추적 코드)

| 파일 | 하는 일 |
|---|---|
| `stage1/geomem/devset.py` | 정의(torch 없음): `dev_frames(data, scene, split)`, `eval_cams`, `basic_set`, `index` |
| `stage1/methods/geomem/dev_decode.py` | 프리셋 하나를 DEV 분할에 디코딩(scsam3): `scripts/docker_run.sh scsam3 python -m methods.geomem.dev_decode --preset <tag> --split A|B [--validate]` → `Data/_dev/<preset>_<split>/` |
| `stage1/methods/geomem/dev_score.py` | 쌍별 J&F와 기준 가시성 해부(scsam3): `... -m methods.geomem.dev_score --masks Data/_dev/<name> --out <json> [--r1]` |
| `stage1/mvseg2d/dev_compare.py` | 두 채점의 짝지은 비교(호스트): 장면 군집 부트스트랩(뷰 = "t/카메라", 10 000, seed 0), 실패/좋은·실패 유형·장면별 |
| `stage1/mvseg2d/paired.py` | `view_key` 인자 추가(기본 "cam" = 키프레임 그대로; DEV는 "view") |

디코딩은 `decode_scene`을 그대로 쓰고, 프레임 t의 이미지·정답·π³ 캐시(`Cache/pi3_frames/<t>`)를 주며, 카메라를 c_ini + 평가 카메라 + 각 평가 카메라의 k=3 후보로 줄입니다(평가 카메라의 결과는 전체 디코딩과 바이트 동일 — `--validate`가 장면마다 첫 프레임에서 확인).

## 3. 등록에서 쓰는 법

1. 후보와 상수는 DEV-A에서만 고르고, 고른 값을 등록 문서에 적습니다(상수마다 DEV-A 근거).
2. 등록 문서에 DEV-B 확인 규칙(통과 조건)을 먼저 적고 커밋한 뒤 DEV-B를 한 번 돌립니다.
3. DEV-B 확인을 통과한 팔만 키프레임 관문(TEST)으로 갑니다. 키프레임 결과는 DEV에서 예측한 범위와 대조합니다.
4. 키프레임의 수치는 DEV 설계에 쓰지 않습니다(이미 공개된 E8~E12 키프레임 분석은 배경 지식으로만).
