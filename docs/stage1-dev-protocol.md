# 1단계 개발 집합(DEV) 규약 — 2026-10-15 채택

> S1-E13에서 처음 쓴 개발 집합 경로를 추적 코드로 옮겨, 앞으로 모든 1단계 등록의 표준으로 삼습니다(사용자 결정 2026-10-15 "너의 추천대로 해줘").
> 동기: S1-E12의 "합성 껍데기"처럼 시험 키프레임에서 설계·측정한 규칙은 정당하게 등록할 수 없었습니다. 설계와 탐색은 키프레임이 아닌 프레임에서 합니다.

## 1. 집합

| 이름 | 프레임 | 용도 |
|---|---|---|
| **TEST** | 각 장면의 기준 프레임(meta `ref_frame`) — 키프레임 664쌍(`MVSeed/runs/seedfail.json`) | 사전 등록한 관문(G1/G2 …)만. 무엇도 여기서 고르거나 조정하지 않음 |
| **DEV-A** (탐색) | 기준 프레임이 아닌 학습 프레임의 [3::4] = ref+4, +8, +12, +16, +20 (장면당 5) | 후보 측정, 상수 고정, 상한 추정. 반복 사용 가능 |
| **DEV-B** (확인) | 나머지 비기준 학습 프레임 15개(ref+1, 2, 3, 5, 6, 7, 9, …, 19) | 등록 하나당 한 번, DEV-A에서 고른 규칙을 확인. 확인 결과를 보고 규칙을 바꾸면 DEV-B는 소진된 것으로 봄 |

- 뷰 = (프레임 t, 카메라) — 주석된 비기준 카메라 2대. 입력 = 기준 카메라 c_ini의 t 시점 정답(장면의 basic 객체 집합으로 제한). 쌍 = (장면, t, 카메라, 객체), c_ini에 객체가 있고 그 카메라 정답이 비어 있지 않은 것(키프레임의 gt_px > 0 규칙과 같음).
- 장면마다 **자기 폴드를 보류한 체크포인트**로 디코딩하므로 DEV 프레임은 그것을 디코딩하는 모델의 학습 데이터에 들어 있지 않습니다(다른 폴드 모델의 학습에는 들어 있음 — 키프레임과 같은 조건).
- DEV-A 3 300쌍(채택 `geoset_rep_x` J&F 0.908), DEV-B 약 3 배.
- 기준을 돌린 집합 DEV-A′·DEV-B′와 기준을 돌린 키프레임의 정의는 §4(2026-10-20 개정)에 있습니다.

## 3. 등록에서 쓰는 법

1. MUVOD에서 후보와 상수는 DEV-A와 DEV-A′(§4)에서만 고르고, 고른 값을 등록 문서에 적습니다(상수마다 DEV-A·DEV-A′ 근거).
2. 등록 문서에 DEV-B 확인 규칙(통과 조건)을 먼저 적고 커밋한 뒤 DEV-B를 한 번 돌립니다.
3. DEV-B 확인을 통과한 팔만 키프레임 관문(TEST)으로 갑니다. 키프레임 결과는 DEV에서 예측한 범위와 대조합니다.
4. 키프레임의 수치는 DEV 설계에 쓰지 않습니다(이미 공개된 E8~E12 키프레임 분석은 배경 지식으로만).

## 4. 기준 회전 집합 DEV-A′·DEV-B′ (2026-10-20 개정)

> 사용자 결정 2026-10-20(S1-E15 U1 승인). 동기: 원래 기준의 MUVOD 쌍은 c_ini → 평가 카메라 시점차가 약 47°를 넘지 않습니다(S1-E15 탐침; 그 등록의 Step 0에서 다시 잼). 그래서 넓은 시점차를 겨냥한 규칙은 DEV-B·키프레임에서 구성상 바이트 동일이 되어, 도메인 내 확인이 공허해집니다. 학습은 주석 카메라 3대의 모든 순서쌍을 쓰므로(`geomem/data.py` `enumerate_samples`) 기준을 돌린 쌍(최대 약 89.7°)은 학습 분포 안입니다.

| 이름 | 프레임 | 기준 | 평가 카메라 | 용도 |
|---|---|---|---|---|
| **DEV-A′** (설계) | DEV-A 프레임 | 원래 기준이 아닌 주석 카메라 r′ 하나(프레임마다 2가지) | 나머지 주석 카메라 2대(원래 c_ini 포함) | DEV-A와 같음: 후보 측정, 상수 고정. 반복 사용 가능 |
| **DEV-B′** (확인) | DEV-B 프레임 | 같음 | 같음 | DEV-B와 함께 등록당 한 번. DEV-B와 같은 소진 규칙, 같은 사용 횟수 한도(DEV-B와 묶어 셈) |
| 기준을 돌린 키프레임 | 기준 프레임 | 같음 | 같음 | **TEST. 디코딩하지 않음.** 어떤 관문도 쓰지 않음 |

- 입력 = r′의 t 시점 정답, 장면의 basic 집합으로 제한. 객체 = r′에 있는 basic 객체.
- 쌍 = (장면, t, r′, 카메라, 객체), r′에 객체가 있고 그 카메라 정답이 비어 있지 않은 것(§1과 같은 규칙).
- 뷰 키 = "t/r′/카메라". 부트스트랩은 장면 군집 그대로(10 000, seed 0). 한 프레임의 두 회전은 같은 장면 군집 안에 있습니다.
- 체크포인트 = 장면마다 자기 폴드를 보류한 것(§1과 같음).
- π³ 프레임 캐시(`Cache/pi3_frames/<t>`)는 그대로 씁니다. 기준은 디코딩 때 r′로 바꿉니다.
- C0(대조) 디코딩도 같은 시점 규칙을 따릅니다. DEV-A′ C0는 설계 단계에서, DEV-B′ C0는 등록의 마지막 커밋(DEV-B 규칙 커밋) 뒤에만 디코딩·채점합니다.
- DEV-A′·DEV-B′의 각도 분포(입력만)는 설계 전에 봐도 됩니다. 평가 카메라 정답과 예측은 위 규칙대로만 읽습니다.
- DEV-B′의 입력(r′의 정답)은 원래 DEV-B 평가 카메라의 정답 라벨 맵입니다. 설계 전에는 그중 basic 객체의 합집합(각도 기준점)과 객체 수만 읽습니다. 화소 단위 비교와 점수는 하지 않습니다(S1-E15 Step 0).
- 도구(S1-E15에서 추가): `dev_decode --ref-rot {0,1,2}`(0 = 원래 기준), `devset`의 기준 회전 정의, `dev_score`의 돌린 기준 읽기와 "다른 객체 마스크" 수, `dev_compare`의 뷰 키.
- 원래 기준의 DEV-A·DEV-B·TEST 정의(§1)는 바꾸지 않습니다.
