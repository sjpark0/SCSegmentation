# S2-R3 사전 등록 — 크롭 추적 문턱을 **1만 → 4.4만 px**으로 올린다

> 2026-09-11. 사용자 지시(2026-09-11 "진행해줘"). [error-budget.md](error-budget.md)가 보인 자리를 겨냥합니다:
> 현재 헤드라인은 시드 **1만 px 미만** 객체만 크롭 추적하는데, 확대 이득이 남아 있는 구간이 **1만~4.4만 px에 351쌍** 더 있습니다.
> 층: **확정**(헤드라인을 바꿀 수 있는 실행). 새 코드 없음 — 플래그 값 하나만 다릅니다.

## 1. 왜 4.4만인가 (계산으로 정해진 값, 데이터를 보고 고른 값이 아님)
`crop_track`의 창은 **시드 박스의 4배**(최소 256 px, 정사각)이고 그것을 **1008 px**로 리사이즈합니다. 게이트 v2는 확대율
`zoom = 1008 / side < 1.2`인 쌍을 되돌립니다. 대략 정사각인 객체의 면적을 A라 하면 `side ≈ 4√A`이므로

> zoom ≥ 1.2 ⟺ 4√A ≤ 840 ⟺ **A ≤ 44,100 px**

문턱을 4.4만보다 더 올려도 새로 들어오는 객체는 게이트 v2가 전부 되돌립니다. 즉 **4.4만은 이 메커니즘의 자연 상한**입니다.

## 2. 알려진 사실 (실행 전)
- 헤드라인 `SegMaskSam3XW1CGPS4MFsCs10kG2` = basic **91.015** / complete **86.4**. 크롭 대상 349쌍, 게이트 되돌림 71, 채택 **278**.
- S2-R1이 시험한 문턱은 2,000과 10,000 둘뿐이고 10,000이 더 좋았습니다(게이트 전 +1.28 대 +0.96). **그 위는 미시험.**
- 오차 예산(정답 면적 중앙값 기준): 1만~4.4만 구간 **351쌍**, 현재 J&F 0.933, 예상 확대율 중앙값 **1.72**, 완벽시 +1.97점.
  4.4만 이상 373쌍은 확대율 0.59로 이 손잡이의 범위 밖입니다.

## 3. 실행
`XVIEW=1 XMODE=C XGATE=1 XPTR=1 XSHIFT=4 XREF=muvod F0SEED=1 CROP=44000 CROPGATE=v2 SCSam3/runMVOptThree.sh <17장면>`
→ `SegMaskSam3XW1CGPS4MFsCs44kG2`. 채점 `eval_jf.py` → `report_jf.py --muvod`. **대조군은 현재 헤드라인** `SegMaskSam3XW1CGPS4MFsCs10kG2`.
게이트·창 규칙·프레임 0 규칙은 R1″/R2에서 고정한 것을 **하나도 바꾸지 않습니다**.

## 4. 판정 규칙(고정)
- **채택**: 17장면 basic Δ(R3 − 헤드라인) ≥ **+0.3점** 그리고 어느 장면도 **< −0.3점**. 통과하면 헤드라인을 `…Cs44kG2`로 교체.
- **기각**: Δ < +0.3 또는 어느 장면이 −0.3 아래. 그러면 문턱 1만을 유지하고, 실패가 확대율 때문인지 다른 이유인지 진단만 보고.
- 보조(중단 규칙 없음): complete, 쌍 수준 짝지은 ΔJ&F의 클러스터 부트스트랩 95% CI(seed 0, 10,000), 장면별 Δ,
  1만 미만 쌍이 헤드라인과 **바이트 동일**한지(새로 들어온 구간만 달라야 함), 새 대상·되돌림 수, 실행 시간.
- 감시: 1만 미만 대상·되돌림 집합이 278/71에서 바뀌면 구현이 예상과 다른 것이므로 원인을 적고 채택 보류.
